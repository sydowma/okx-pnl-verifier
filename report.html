一、执行摘要（Executive Summary）

二、业务背景与方案演进对比

最初设想的公式为 totalEq(Now) - NetTransfers - totalEq(T0)。经过实盘验证，虽然该公式可通过 bills-archive + fills-history + 历史 K 线实现还原，但在生产环境中存在明显短板：

  • 接口重、分页深：高频交易用户单月账单可达数万条，全量拉取 bills 和 fills 成本极高；
  • 现货波动污染榜单：实测发现你 Demo 账户 11 月未做任何交易，仅因持有 BTC/ETH/OKB 现货下跌，totalEq 权益法算出 -$21,489，无法真实反映合约交易水平；
  • 划转口径易漏：不能只查充提，必须从交易账户账单筛选 type == "1" 才能覆盖资金账户与交易账户之间的内部划转。

因此，我们将方案演进为轻量化仓位增量方案（方案 C），两者对比如下：

对比维度 原方案：总权益法（totalEq + bills） 推荐方案：仓位增量法（positions + WS）
核心口径 账户总权益变化（含现货持仓涨跌） 纯合约交易 PnL（已含手续费、资金费、强平费）
依赖 REST 接口 balance + bills + bills-archive + fills-history + 历史 K 线 仅 positions + positions-history（冷启动各 1 次）
实时更新机制 WS account + 仍需持续追踪划转流水 WS positions 纯内存增量 + 全平事件单条查库
资金划转影响 强相关（漏一笔划转榜单即错误） 完全免疫
现货持仓波动 会直接计入榜单 PnL 完全隔离
工程复杂度 重（高频分页 + 对账复杂） 极轻（状态机清晰，易于横向扩展）

MonthlyPnL(T0 → Now) = closed_pnl_usd + Σ open_positions_pnl_usd • 月内新开仓位 (cTime >= T0)：单仓位贡献 = (realizedPnl + upl) × ccy_usd_px • 跨月老仓位 (cTime < T0)：单仓位贡献 = (realizedPnl + upl) × ccy_usd_px - snapshot_pnl(T0)

4.1 深度解析：为什么无 1 号快照时，只用 positions 无法做到 100% 精确？

本质上是 OKX 仓位接口的数据模型限制，共有 3 个无法绕过的底层原因：

原因 1：OKX 不提供「历史时间点快照」查询能力
GET /api/v5/account/positions 只能查询此刻（Now）的实时持仓，不支持传入 ts=11月1日00:00 查询历史某瞬间的持仓状态。

原因 2：手续费、资金费率与部分平仓盈亏均为「全生命周期单一累计数」，无法按时间切分
positions 与 positions-history 返回的 fee、fundingFee、realizedPnl 都是从开仓时刻（cTime）一直累加到现在的总和。
举例：用户 10 月 25 日开仓（开仓费 -$5），10 月 26～31 日扣资金费 -$30，11 月 1～10 日扣资金费 -$20。接口只给你一个汇总值 fundingFee = -$50，单靠仓位接口无法得知其中 -$30 发生在 10 月、-$20 发生在 11 月（必须查 bills-archive 按时间戳过滤）。

原因 3：跨月期间若存在加仓或部分平仓，无法唯一反推 1 号 0 点时的张数 pos(T0) 与均价 avgPx(T0)
计算 1 号 0 点浮盈需要公式 UPL(T0) = pos(T0) × ctVal × (markPx(T0) - avgPx(T0))。
举例：用户 10 月 25 日开多 10 张，11 月 2 日加仓 5 张，11 月 5 日平掉 8 张，当前仅剩 7 张（或全平后 positions-history 只给 openMaxPos=15）。单靠仓位接口不知道 11 月 1 日 00:00 那一瞬间手里到底是 10 张还是 15 张、当时开仓均价是多少（必须查 fills-history 从当前状态按成交逐笔倒推）。

5.2 延迟队列如何确定「是否已查到」？（关键关联主键：(posId, cTime)）

注意：千万不能只用 posId 判重！
实测你的 SOL-USDT-SWAP 历史记录发现，OKX 在同一合约/方向/保证金模式下每次开平都会复用同一个 posId（5 笔不同时间开平的交易全部为 posId=4128004816484012033）。如果只判断 posId 是否存在，在 1～2 秒索引延迟期间一定会误命中上一笔旧交易！

正确的确定性关联规则（毫秒级精确一致）：
• WS 全平帧：posId=4128004816484012033, cTime=1795527361799, uTime=1795527369441
• REST 历史行：posId=4128004816484012033, cTime=1795527361799, uTime=1795527369441, realizedPnl=-0.105937
延迟队列处理闭环：
1. 收到 pos=="0" 后，先将仓位移入 pending_close 保持原 PnL（防止榜单瞬间抖动），并将 (uid, instId, posId, cTime, uTime) 写入持久化延迟队列；
2. 队列按 1s → 2s → 5s → 15s → 60s 退避调用 GET /positions-history?instId=...&limit=5；
3. 命中判定条件：row.posId == posId && row.cTime == cTime（可附加 row.uTime >= close_uTime）；命中后原子写入 user_closed_positions 并删除 pending_close，未命中则继续下一次重试。

6.2 核心字段映射（REST 与 WS 字段完全同名）

字段名 来源 字段含义 在计算中的具体作用
instId REST / WS 合约 ID（如 BTC-USD-SWAP） 与 posSide、cTime 组成唯一仓位主键 pos_key。
posSide REST / WS 持仓方向（net / long / short） 区分单向持仓与双向持仓的多空方向，防止同一合约多空互相覆盖。
cTime REST / WS 仓位创建时间（毫秒时间戳） 最关键主键：① 判断 cTime < T0（跨月老仓）还是 cTime >= T0（月内新仓）；② 全平查 positions-history 时做严格精确匹配，防止串单。
uTime REST / WS 仓位最新更新时间（毫秒） 平仓后用于筛选本月平仓记录（uTime >= T0），以及作为币本位折算 USD 的时间戳。
pos REST / WS 当前持仓张数 pos != "0" → 持仓中，纯内存更新；pos == "0" → 触发全平落袋逻辑。
ccy REST / WS 保证金/结算币种（USDT / USDC / BTC） 决定盈亏单位：稳定币直接 × 1.0；币本位（如 BTC）必须乘以 USD 汇率。
realizedPnl REST / WS 仓位累计已实现盈亏（单位为 ccy） OKX 已自动汇总：realizedPnl = 平仓盈亏(pnl) + 手续费(fee) + 资金费(fundingFee) + 强平罚金(liqPenalty) + 结算盈亏(settledPnl)。注意：WS pos=="0" 帧会将其清空为 ""。
upl REST / WS 按标记价格计算的未实现盈亏（单位为 ccy） 与 realizedPnl 相加得到活跃仓位的当前全生命周期总盈亏。
idxPx / markPx WS positions 标的指数价 / 标记价 币本位持仓期间直接取 WS 自带的 idxPx（兜底 markPx）将 BTC/ETH 盈亏实时折算为 USD，省去额外行情请求。

八、完整生产方案：两大核心场景评估（10 万存量预热 + 月中新用户补录）

结合「持久化落库 + 服务重启容灾 + 1 号 0 点提前上线预热 + 月中动态插入新用户」的完整业务背景，整个生产系统可拆解为两大标准场景，均采用 Redis（实时热状态 + ZSET 排行榜）+ 关系型 DB（持久化 + 唯一键幂等） 支撑。

接口期限提醒：OKX 的 GET /api/v5/account/bills 仅保留近 7 天；只要回溯超过 7 天（如 1 个月内），就必须调用 GET /api/v5/account/bills-archive（保留近 3 个月）。好消息是：在下面这套双场景方案中，场景一完全不需要 bills，场景二绝大多数用户也不需要 bills。

8.1 场景一：1 号 0 点前提前上线（10 万存量候选集）

核心思路：在 1 号 0 点之前提前把 10 万用户的「持仓状态 + WS 长连接」平滑预热进 Redis/DB；到 00:00:00.000 这一瞬间，完全不调任何用户级 REST 接口，而是用 1 份全平台共享的 0 点标记价表在本地毫秒级完成全部 10 万用户的统一快照。

快照粒度选型：monthly_position_snapshots 必须按仓位维度存吗？能改成按用户存 1 条吗？
• 不能存成用户总资产 totalEq(T0)：资产快照只能配合 totalEq - NetTransfers 权益法使用，无法与 positions 仓位法混用。
• 可以汇总成用户级「0 点持仓总盈亏」单值（user_t0_pos_pnl = Σ(realizedPnl@T0 + upl@T0)）：从代数上，T0 时刻未平的每个仓位要么此刻仍未平、要么已在本月平仓，因此对用户级月度总 PnL 而言，存 1 条用户级汇总值（10 万行/月）与按仓位明细存储数学完全等价。
• 何时保留仓位级明细表：需要前端展示「单个仓位本月赚了多少」、或需要逐合约对账/排查 pending_close 与月中补数明细时，保留仓位维度表更便于审计。
综合评估结论：
• 场景一（10 万提前预热用户）：预热期匀速平滑拉取（~30–55 QPS），0 点 0 次 OKX REST、0 毫秒价格偏移、100% 精确。
• 场景二（月中新用户）：通过「月内桶 / 跨月桶」两级分流，绝大多数无跨月仓位用户 2 次 REST（~200ms）即精确入榜；少数有跨月老仓的用户仅针对特定 instId 异步补齐一次 T0 基线后永久切回 WS 增量，兼顾了高并发效率与从 1 号 0 点起算的 100% 准确性。

九、生产落地清单与 4 大必避深坑

坑 1：WS 全平帧（pos == "0"）清空盈亏字段
OKX 在全平推送中将 realizedPnl / pnl / fee / upl 全部置为空串 ""，切勿直接按 0 入账；必须由 pos == "0" 事件触发查 1 次 positions-history。

坑 2：positions-history 约 1～2 秒索引延迟
收到 pos == "0" 后若立刻查并盲取第 1 条，可能串单拿到上一个已平仓位。必须严格按 cTime == ws.cTime 精确匹配并加短退避重试（1s / 2s / 3s）。
坑 3：币本位合约（ccy = BTC / ETH）的 USD 折算
币本位合约的 realizedPnl 与 upl 单位为币本身而非 USD。持仓中直接取 WS 帧自带的 idxPx 折算（无需额外 REST），全平落袋时按 uTime 对应指数 K 线折算 USD。

坑 4：WebSocket 端口与通知帧兼容
OKX 8443 端口即将下线，连接时会先发 code: 64010 的 notice 帧。生产环境请直接使用 443 端口（wss://ws.okx.com/ws/v5/private），并在鉴权收包循环中跳过 notice 事件。

建议研发落地顺序

  1. 权限控制：引导用户仅提供 只读（Read-Only）+ IP 白名单 的 OKX API Key 即可跑通本方案全部功能。
  2. 定时基线任务：部署每月 1 日 00:00:00 定时任务，对所有绑定用户调用 1 次 GET /api/v5/account/positions 落库 snapshot_pnl(T0)。
  3. 增量服务部署：每个用户维护 1 条 443 端口私有 WS 连接（订阅 positions / ANY），断线重连时自动执行 2 次 REST 重新对齐内存状态。
  4. 排行榜防刷扩展（可选）：如后续需要按收益率（ROI %）排名而非绝对盈亏额，建议引入时间加权收益率（TWR）或 Modified Dietz 公式防止中途大额充提刷榜。
